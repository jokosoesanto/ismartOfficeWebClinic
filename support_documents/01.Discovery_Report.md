# Executive Summary

Dokumen ini merupakan hasil Discovery dan Reverse Engineering mendalam terhadap source code aplikasi desktop **iSmartOffice**. Tujuan dari analisis ini adalah untuk memberikan landasan komprehensif bagi proyek modernisasi dan migrasi aplikasi menuju arsitektur web modern menggunakan **ASP.NET Core** dan **PostgreSQL**.

Analisis menunjukkan bahwa aplikasi saat ini dibangun menggunakan arsitektur **WinForms 3-Tier** klasik di atas **.NET Framework 3.5**. Aplikasi ini memiliki ketergantungan erat pada pustaka pihak ketiga yang sudah _legacy_ (ActiveReports 3, ComponentGo, dll.), serta integrasi perangkat keras/medis yang sangat spesifik (Cephalometric analysis via `JoeCeph32`). 

Proses migrasi memiliki kompleksitas yang **High** hingga **Very High** di beberapa modul (khususnya Dental Charting & Digital Imaging) karena tingginya _coupling_ antara UI dan Business Logic, serta ketiadaan _separation of concerns_ yang memadai. Strategi migrasi yang direkomendasikan adalah pendekatan **Backend First** dengan membangun ulang _core business logic_ sebagai RESTful API sebelum menyentuh antarmuka pengguna.

# Architecture Assessment

## Technology Stack
- **Platform**: Windows Desktop (WinForms)
- **Framework**: .NET Framework 3.5
- **Target Architecture**: x86 / AnyCPU
- **Database Engine**: Microsoft SQL Server (Inferred from `SqlConnection`, `app.config`, & `SqlHelper`)
- **Data Access**: ADO.NET (Custom `SqlHelper` / Active Record Pattern via `iSmartOfficeHelper.Data` & `iSmartOfficeHelper.Biz`)

## Third-party Library & Dependency Map
Berdasarkan berkas `.csproj` dan direktori `DLL`, berikut adalah dependensi yang ditemukan:
1. **ActiveReports 3** (`ActiveReports3.dll`, dll.): Digunakan untuk _reporting engine_ (pembuatan laporan, ekspor PDF/Excel, Claims).
2. **ComponentGo.Calendars** (`ComponentGo.Calendars.dll`): Komponen UI untuk _Scheduling_ dan _Calendar_ kalender praktek/dokter.
3. **LumiSoft.UI** (`LumiSoft.UI.dll`): Pustaka UI tambahan (kemungkinan untuk TreeView atau layouting).
4. **PinkieControls** (`PinkieControls.dll`): Pustaka _custom controls_ UI.
5. **JoeCeph32.Library** (`JoeCeph32.Library.dll`): Pustaka spesifik _domain_ ortodonti untuk analisis sefalometri (Cephalometric analysis).
6. **TeethSurface** (`TeethSurface.dll`): Pustaka natif/spesifik untuk rendering _Dental Chart_ (Odontogram).
7. **Web Services (SOAP)**:
   - License Service: `https://ismartoffice-secure.ismartdds.com/service.asmx`
   - BioProgressive Service: `http://bioprogressive.org/service.asmx`

## Project Structure & Layer Architecture
Solusi `iSmartOffice2012.sln` memiliki 2 project utama dan terhubung dengan layer bisnis terpisah:
1. **`iSmartOfficeClient`**: Main executable. Berisi antarmuka pengguna (Form), reporting, dan _code-behind_.
2. **`iSmartOfficeCheckIn`**: Modul Kiosk/Check-in terpisah untuk digunakan oleh pasien/resepsionis secara mandiri.
3. **`iSmartOfficeHelper.Biz` (DLL)**: Layer _Business Logic_ yang mengenkapsulasi objek entitas (_Active Record_).
4. **`iSmartOfficeHelper.Data` (DLL)**: Layer _Data Access_ yang berkomunikasi langsung dengan database.

**Architecture Pattern**: **3-Tier Architecture** klasik. 
Meskipun dipisah menjadi 3 _layer_ secara fisik (DLL), namun implementasinya lebih menyerupai *Smart UI / Fat Client* dikarenakan objek Biz langsung diinisiasi dan di-binding pada level UI. Tidak ditemukan penggunaan _Dependency Injection_ (DI) atau pattern MVVM/MVP yang ketat.

# Database Discovery

## Tinjauan Database
- **Engine**: Microsoft SQL Server (Diidentifikasi dari penggunaan `System.Data.SqlClient`, kelas `SqlCommand`, `SqlDataReader`, dan _connection string_ format SQL Server `(local)\iSmartDB`).
- **ORM**: Tidak ada ORM modern (seperti Entity Framework atau Dapper). Aplikasi menggunakan **ADO.NET Murni** yang dibungkus di dalam kelas utilitas kustom bernama `SqlHelper.cs` (mengadaptasi pola _Microsoft Enterprise Library Data Access Block_).
- **Stored Procedures**: Sangat bergantung pada _Stored Procedure_. Kelas `SqlHelper` secara rutin menggunakan `CommandType.StoredProcedure` dan melakukan pencarian parameter otomatis (`SqlHelperParameterCache.GetSpParameterSet`).

## Database Reconstruction & Entity Relationship Diagram (ERD)
Karena skema database murni (`.sql` files) tidak disertakan secara utuh, _reverse engineering_ dilakukan dengan mengekstrak kelas entitas dari namespace `iSmartOfficeHelper.Biz` dan menganalisis _data binding_ di UI.

### Tabel Utama & Referensi Skema (Inferensi, Confidence Level: 90%)

#### 1. Modul Core & Administrasi
- **`UserAccount`**: `UserName` (PK), `Password`, `FullName`, `DoctorID` (FK), `IsEnabled`, `JoinSystem`, `LastAccess`.
- **`Location`**: `LocationId` (PK), Cabang/Klinik.
- **`Chair`**: `ChairId` (PK), `LocationId` (FK), `ChairName`.
- **`License`**: Manajemen lisensi aplikasi per mesin.

#### 2. Modul Pasien (Patient)
- **`Patient`**: `PatientId` (PK), `FirstName`, `LastName`, `BirthDate`, `Gender`, `Address`, `Phone`, `Status`, dsb.
- **`Guardian`**: Orang tua/wali pasien.
- **`Patient_Insurance`**: Mapping pasien ke perusahaan asuransi (Lookup/Transaction).
- **`Patient_OrthoDiag` / `Patient_DigitalImage`**: Tabel riwayat diagnostik ortodontik dan rekam foto radiografi/sefalometri pasien.

#### 3. Modul Kunjungan & Dokter (Appointment)
- **`Doctor`**: `DoctorId` (PK), Profil dokter.
- **`Doctor_Schedule`**: Jadwal praktik (shift) dokter.
- **`Appointment`**: `AppointmentId` (PK), `PatientId` (FK), `DoctorId` (FK), `ChairId` (FK), `AppointmentStartTime`, `AppointmentStatus`, `VisitPurpose`.
- **`Appointment_CheckIn`**: Rekam jejak waktu tunggu/kedatangan pasien.

#### 4. Modul Perawatan (Treatment)
- **`TreatmentCategory`**: Kategori perawatan (Master).
- **`TreatmentItem`**: `TreatmentItemCode` (PK), `TreatmentCategoryId` (FK), `TreatmentItemName`, `DefaultPrice`.
- **`Appointment_Treatment`**: _Transaction table_ untuk perawatan spesifik yang dilakukan pada sebuah kunjungan.

#### 5. Modul Keuangan (Payment)
- **`Payment`**: `PaymentId` (PK), `AppointmentId` (FK), `PaymentDate`, `PaymentAmount`, `PaymentMethod`, `CreditCardNo`, `PaymentStatus`.

#### 6. Modul Inventori (Inventory)
- **`InventoryItem`**: `ItemId` (PK), `ItemGroupId` (FK), `SupplierId` (FK), `UnitId` (FK), `ItemName`, `SafeQty`, `OrderQty`.
- **`Supplier`**, **`Warehouse`**, **`WarehouseItem`**, **`InventoryUnit`**, **`InventoryItemGroup`**: Tabel Master pendukung.
- **`InventoryTransaction`**: _History table_ mutasi barang (masuk/keluar).

# Business Module Catalog & Process Mapping

Berdasarkan struktur _form_, modul bisnis dikategorikan sebagai berikut:

1. **Authentication & Administration**
   - **Purpose**: Mengelola login pengguna, hak akses modul (`UserModule`), dan lisensi mesin.
   - **Business Rule**: Enkripsi koneksi database, pengecekan lisensi mesin ke web service eksternal.

2. **Patient Registration & Demographics**
   - **Purpose**: Input data primer pasien beserta _medical alert_ dan penanggung jawab (Guardian).
   - **Workflow**: Pendaftaran Pasien Baru -> Pengisian Riwayat Kesehatan -> Mapping Asuransi.

3. **Appointment & Check-In (Queue)**
   - **Purpose**: Manajemen jadwal pertemuan dan antrean (_Office Console_). Terdapat modul Kiosk/CheckIn mandiri (`RMOfficeCheckIn`).
   - **Workflow**: Booking Jadwal -> Pasien datang (Check-in via Kiosk) -> Status berubah menjadi "Menunggu" -> Dipanggil ke kursi (Chair) tertentu.

4. **Medical Record (Dental Chart & Digital Image)**
   - **Purpose**: Perekaman rekam medis gigi (Odontogram) dan foto medis (Radiografi/Lateral Digitize).
   - **Dependency**: Modul ini sangat bergantung pada interop dengan `TeethSurface.dll` dan `JoeCeph32.Library`.

5. **Billing & Claim (Payment)**
   - **Purpose**: Perekaman pembayaran kasir dan pencetakan klaim asuransi gigi (ADA Claim, Canadian Claim).
   - **Workflow**: Perawatan Selesai -> Tagihan Terbentuk -> Pembayaran (Tunai/CC) -> Cetak Kuitansi / Cetak Form Klaim Asuransi.

6. **Inventory Management**
   - **Purpose**: Melacak stok _dental supply_.
   - **Workflow**: Master Barang -> Stok Masuk (Supplier) -> Mutasi Stok (InventoryTransaction) -> Peringatan _SafeQty_.

7. **Custom Reports**
   - **Purpose**: Pembuatan laporan dinamis (Query Builder kustom `OleDbSchema`).
   - **Output**: Laporan berbasis ActiveReports.

# Source Code & Code Quality Assessment

- **Code Behind Pattern**: Logika bisnis (pengambilan entitas, validasi input, _state management_) digabungkan secara _inline_ di file `.cs` dari form UI. Hal ini berakibat pada **High Coupling** dan **Low Cohesion**.
- **Active Record Usage**: Objek seperti `Location` mengambil datanya dengan memanggil _static method_ `Location.GetLocation(LocationId)` lalu melakukan `Location.Update(_location)`. Pola ini memudahkan _rapid development_ desktop namun sangat rentan masalah konkurensi (Thread Safety) untuk skala web multi-user.
- **Technical Debt**: _Legacy dependencies_ (ActiveReports 3, ComponentGo) yang sudah tidak _supported_ untuk .NET Core/Web. 
- **Security Assessment**: `app.config` menyimpan password database dalam bentuk string _Base64/Encrypted_. Pada migrasi web, hal ini harus dipindahkan ke _Secret Manager_ atau environment variables. Tidak ditemukan kontrol otorisasi (RBAC) yang terpusat di _business layer_, kontrol tersebut berada di UI (Show/Hide menu berdasar hak akses `UserModule`).

| Module | Complexity | Justification |
|--------|------------|---------------|
| **Admin & Auth** | Low | CRUD sederhana. Autentikasi mudah dimodernisasi menggunakan JWT/ASP.NET Core Identity. |

# Risk Assessment & Mitigation

| Risk Area | Description | Mitigation Strategy |
|-----------|-------------|---------------------|
| **UI Coupling** | Logika perhitungan dan bisnis menempel di file Form. | Lakukan ekstraksi logika ke _Service Layer_ terpisah (Backend) tanpa membawa reference UI. |
| **Native / COM Dependency** | Ketergantungan pada `JoeCeph32` untuk medis. DLL ini dirancang untuk arsitektur desktop 32-bit (x86). | *Opsi 1*: Buat Microservice khusus (.NET Framework) untuk membungkus fungsionalitas ini. *Opsi 2 (Ideal)*: Reverse-engineer pustaka ini atau cari ekuivalen pustaka medis open-source. |
| **Report Engine Lock-in** | Menggunakan ActiveReports 3 yang kuno dan tidak _web-friendly_. | Desain ulang laporan menggunakan PDF Generator modern (misal: iText7, QuestPDF) di backend, atau Web Reporting tools (Stimulsoft). |
| **Stored Procedures** | _Heavy reliance_ pada eksekusi SP kustom. Logika yang tertanam di DB tidak mudah _source-controlled_. | Pada saat migrasi ke PostgreSQL, migrasikan Stored Procedure ke PostgreSQL Functions (PL/pgSQL), atau pindahkan logikanya ke lapisan aplikasi (C#) dan gunakan EF Core. |

# Modernization Strategy & Roadmap

Strategi migrasi berpegang teguh pada prinsip **Backend First**, **Business Logic First**, **Parity Verification**, dan **UI Last** untuk menghindari regresi.

## Tahap 1: Database Migration (SQL Server -> PostgreSQL)
- **Skema Dasar**: Transformasi T-SQL DDL ke PostgreSQL DDL (Tabel, PK, FK, Constraints).
- **Stored Procedures**: Menerjemahkan dan/atau menarik logika bisnis dari _Stored Procedure_ ke _C# Domain Services_.
- **Data Migration**: Ekspor dan Verifikasi data historis.

## Tahap 2: Backend First (ASP.NET Core API Development)
- **Architecture**: Menerapkan arsitektur _Clean Architecture_ atau N-Tier modern.
- **ORM**: Mengganti `SqlHelper` (ADO.NET) dengan **Entity Framework Core** (Npgsql).
- **Core Modules**: Membangun endpoints API untuk Modul Admin, Patient, dan Inventory.
- **Test Parity**: Membangun _Unit/Integration Test_ membandingkan output API dengan output _Business Entity_ (Biz.dll) lama.

## Tahap 3: Complex Backend Services (Integrasi Medis & Klaim)
- **Cephalometric / Charting API**: Menyediakan endpoint untuk menyimpan matriks/koordinat _dental chart_ format JSON alih-alih binary state.
- **Reporting Service**: Membangun engine dokumen PDF untuk faktur dan Klaim ADA/Canadian.

## Tahap 4: Frontend Development (Web UI)
- Membangun antarmuka modern (SPA dengan React/Vue/Angular atau MVC/Blazor) yang hanya bertugas sebagai _consumer_ dari Web API.

# Sprint Recommendation

Berdasarkan analisis risiko dan kompleksitas, rekomendasi untuk **Sprint 1 (Smallest Vertical Slice)** adalah:

**"Modernisasi Modul Master Data Administrasi (Location, Chair) & Autentikasi"**

**Goal**:
Membangun fondasi struktur proyek ASP.NET Core dan PostgreSQL, melakukan migrasi satu vertikal fitur dari basis data, backend API, hingga integrasi database.

**Alasan (Mengapa aman & risiko rendah)**:
- Tidak memiliki dependensi dengan _Native Medical Libraries_ (JoeCeph).
- Tidak melibatkan _complex printing_ (ActiveReports).
- Modul ini memiliki struktur tabel yang sederhana namun terintegrasi ke seluruh entitas lain (`Location` & `Chair` dipakai di `Appointment`).
- Keberhasilan sprint ini membuktikan bahwa _pipeline_ koneksi ASP.NET Core ke PostgreSQL berfungsi dengan baik, pola _Repository/Service_ telah terdefinisi, dan siap direplikasi untuk modul yang lebih kompleks pada Sprint 2 (Patient & Inventory).
